# Sprint 2.2 — Developer Experience & CI Audit

**Date:** 2026-07-23
**Branch:** `feature/vie-quotation`
**Objective (verbatim):** *"Perform a Developer Experience and CI audit.
Eliminate the root causes that repeatedly generate formatting and lint
failures. Standardize formatting, linting, generated-file handling,

## 1. Summary

`docs/CI_LINT_DEBT.md` (2026-07-18) documented ~7,409 ESLint problems
across ~315 files and left CI's Lint step permanently softened
(`continue-on-error: true`, added in Sprint 1.9 Milestone 4) as a
stopgap. Re-auditing that debt from scratch, rather than accepting the
315-file framing at face value, found that:

- **7,385 of the 7,391 errors (99.9%) were a single file**:
  `src/integrations/supabase/types.ts`, an auto-generated Supabase types
  file that had never been excluded from ESLint the way
  `src/routeTree.gen.ts` already was.
- **A second, previously undiscovered generated-file gap**: the four
  route files emitted by the `@lovable.dev/mcp-js` Vite plugin
  (`mcpPlugin()` in `vite.config.ts`) also were not excluded, and would
  have re-failed lint/format on every dev/build regeneration regardless
  of any manual fix.
- **The real, non-generated debt was 5 files**, not 315 — the bulk of
  the original 315-file count had already been cleaned up by commits
  made between 2026-07-18 and now; what remained was one component
  (`SmartInputs.tsx`) with genuine formatting drift, plus the 4
  generated route files above (which only need exclusion, not
  reformatting).

With both generated-file categories excluded and the 5 real files fixed,
`eslint .` now exits **0 errors** (18 pre-existing, non-blocking
`react-hooks`/`react-refresh` warnings remain — see §5). CI's Lint step
no longer needs `continue-on-error` and has been restored to a real,
blocking gate.

A pre-commit hook (husky + lint-staged) was designed and validated but
**could not be installed in this sandbox** — see §4 for why, and the

## 2. Root cause: generated files never excluded from lint/format tooling

Both `.prettierignore` and `eslint.config.js` already had a working
precedent — `src/routeTree.gen.ts` — excluded from Prettier via
`.prettierignore` and self-excluded from ESLint via its own inline
`/* eslint-disable */` banner. That pattern was never extended to the
other two classes of generated file in this repo:

### 2a. `src/integrations/supabase/types.ts`

Generated by `supabase gen types typescript` (documented in
`docs/authentication.md`). It carries no `/* eslint-disable */` banner
(unlike `routeTree.gen.ts`), so ESLint linted it in full — 9,224 lines,
formatted in the Supabase CLI's own style, not this repo's
`.prettierrc` (`printWidth: 100`, `semi: true`, `singleQuote: false`).
Every regeneration reintroduces the same ~7,385 `prettier/prettier`
violations, which is exactly what happened between 2026-07-18 and now
(`git log` shows the file was reformatted once, at commit `9212e11`
"Apply Prettier formatting", then drifted right back out — consistent
with a later regeneration overwriting that fix).

**Fix:** added to both `.prettierignore` and `eslint.config.js`'s
`ignores` array, with a comment explaining why (see diffs in §6).

### 2b. The four `@lovable.dev/mcp-js`-generated route files

`vite.config.ts` calls `mcpPlugin()` (from
`@lovable.dev/mcp-js/stacks/tanstack/vite`) with no config, which
regenerates four fixed route files on every dev/build run:

- `src/routes/mcp.ts`
- `src/routes/[.mcp]/list-tools.ts`
- `src/routes/[.mcp]/invoke-tool/$tool.ts`
- `src/routes/[.well-known]/oauth-protected-resource.ts`

Each carries its own banner:

```
// AUTO-GENERATED by @lovable.dev/mcp-js — do not edit. Regenerated by the Vite plugin.
// To take ownership, delete this banner line; the plugin then leaves the file alone.
```

None of the four were excluded from ESLint or Prettier, so all four
appeared in every lint run with the same single-line-object-literal
`prettier/prettier` violation (the plugin emits
`{ resourcePath: "/mcp", metadataPath: "...", trustForwardedHost: true }`
as one line; this repo's Prettier config wraps it across lines once it
exceeds `printWidth: 100`). Running `prettier --write` on them "fixes"
the immediate lint output, but the fix is inert — the very next
`vite dev` or `vite build` regenerates the file from the plugin's own
template and the violation reappears. This was confirmed directly: an
initial fix attempt in this sprint appeared to succeed, then silently
reverted after an unrelated `npm run build` regenerated the files
mid-session.

**Fix:** added to both `.prettierignore` and `eslint.config.js`'s
`ignores` array (bracket-escaped — see note below), matching the
`types.ts` treatment.

**Note on the escaping:** the route paths `[.mcp]` and `[.well-known]`
contain literal square brackets from TanStack Start's file-based routing
convention. Both `.prettierignore` (gitignore-style patterns) and
`eslint.config.js` (minimatch-style globs) treat unescaped `[...]` as a
character class, not literal brackets — an unescaped pattern would
silently fail to match (or match the wrong thing) rather than error.
Both files use `\[` / `\]` to match the literal path segments; this was
verified directly (`npx eslint <path>` before/after showed the "File
ignored because of a matching ignore pattern" message only once escaped
correctly).

### 2c. Policy for future generated files

If a future code generator (Supabase, a Vite plugin, the TanStack router
generator, or anything else) starts emitting files into `src/`, treat it
the same way: either have the generator emit its own
`/* eslint-disable */` banner (as `routeTree.gen.ts`'s generator already
does), or add the emitted path to both `.prettierignore` and
`eslint.config.js`'s `ignores`. Don't run `prettier --write` /
`eslint --fix` on a generated file as a one-off fix — it doesn't survive
the next regeneration and just reappears in the next lint run.

## 4. Pre-commit enforcement (husky + lint-staged) — designed, not installed

### What was built and verified

- `.husky/pre-commit` running `npx lint-staged`.
- A `lint-staged` config in `package.json`:
  ```json
  "lint-staged": {
    "*.{ts,tsx}": ["eslint --fix", "prettier --write"],
    "*.{js,jsx,json,css,md}": ["prettier --write"]
  }
  ```
- `"prepare": "husky"` script (the standard husky v9 wiring — runs on
  every `bun install`/`npm install`, sets `core.hooksPath` to `.husky`).

This was scaffolded and test-run locally in this sandbox (via a
temporary `npm install` of `husky`/`lint-staged` from the public npm
registry — see below) and works correctly.

### Why it isn't committed

This repo's canonical package manager is `bun` — CI runs
`bun install --frozen-lockfile`, and `bun.lock` is the lockfile that
governs. Adding `husky`/`lint-staged` to `package.json`'s
`devDependencies` without a matching `bun.lock` update would make
`bun install --frozen-lockfile` fail on **every future push**, since
frozen-lockfile mode refuses to proceed when the lockfile doesn't
exactly satisfy `package.json`. That would break the Install step CI
runs before Lint even starts — a regression directly opposed to this
sprint's goal.

Regenerating `bun.lock` requires `bun` to reach every package's resolved
registry URL. This repo's existing `bun.lock` entries are pinned to a
private mirror
(`https://europe-west{1,4}-npm.pkg.dev/lovable-core-prod/sandbox-npm-cache/...`)
that is **completely unreachable from this sandbox** — confirmed with a
direct `curl` (connection failure, not just a 403) and with four
separate `bun install`/`bun add` attempts (`--offline`, with
`BUN_CONFIG_REGISTRY` overridden, and combinations of both), all of
which failed identically. This is a sandbox network-allowlist gap (only
`registry.npmjs.org` and a handful of other public registries are
reachable; the project's actual mirror is not), not a credentials
problem this session can resolve, and not something to work around by
disabling lockfile verification or hand-editing `bun.lock`'s pinned
URLs.

`npm install` against the public `registry.npmjs.org` (which *is*
reachable) was used **only** to locally verify the hook configuration
works and to restore a working `node_modules` for this sprint's own
`typecheck`/`lint`/`test`/`build` verification — package-lock.json was
reverted afterward (`git checkout -- package-lock.json`) and is
untouched in the final diff. It is not a substitute for updating
`bun.lock`, since npm's own dependency resolution (and even its choice
of `prettier`/`eslint` patch versions within this repo's existing
semver ranges) does not match what `bun install --frozen-lockfile`
actually installs in CI — this was directly observed mid-sprint: npm
resolved `prettier@3.9.5` where `bun.lock` pins `prettier@3.8.3`, and
the two versions format multi-line union types differently, producing
13 false-positive lint errors that vanished once the exact `bun.lock`-
pinned tool versions (`prettier@3.8.3`, `eslint@9.39.4`,
`eslint-plugin-prettier@5.5.5`, `eslint-config-prettier@10.1.8`,
`typescript-eslint@8.59.0`) were installed instead. All verification
numbers in this document (§1, §5) are from that exact pinned toolchain,
not npm's default resolution.

### Exact steps to finish this, in an environment with registry access

Run from the repo root, on `feature/vie-quotation` (or after it's
merged):

```bash
bun add -d husky lint-staged
bunx husky init
```

Then replace the auto-generated `.husky/pre-commit` content
(`npm test`) with:

```
npx lint-staged
```

And add this block to `package.json` (alongside the existing `"pnpm"` /
`"overrides"` keys):

```json
"lint-staged": {
  "*.{ts,tsx}": ["eslint --fix", "prettier --write"],
  "*.{js,jsx,json,css,md}": ["prettier --write"]
}
```

`bun add` will update `bun.lock` correctly since it runs with real
registry access. Commit `package.json`, `bun.lock`, and
`.husky/pre-commit` together (`.husky/_/` is husky's own regenerated
internal directory — it ships its own `.gitignore` and should not be
committed).

## 5. Remaining lint output (non-blocking, out of scope)

`eslint .` now exits 0 (no errors) but reports 18 pre-existing
warnings, which do not fail CI (the `lint` script has no
`--max-warnings` flag) and were deliberately left alone:

- **11× `react-refresh/only-export-components`** — almost entirely
  shadcn/ui primitives (`button.tsx`, `badge.tsx`, `alert.tsx`,
  `card.tsx`, `form.tsx`, `navigation-menu.tsx`, `sidebar.tsx`,
  `toggle.tsx`) exporting both a component and a co-located
  variant/helper function (e.g. `buttonVariants` alongside `Button`) —
  the standard, expected shadcn/ui pattern, not a defect.
- **5× `react-hooks/exhaustive-deps`** — real hook-dependency signals in
  `NotificationsBell.tsx`, `use-roles.tsx`, `calendar.tsx`,
  `communication.tsx`, `estimates/index.tsx`. Each needs a logic
  decision (does adding the dependency change render behavior?) that
  this audit's scope — tooling/workflow standardization — is not the
  right context to make blind. Flagging here rather than silently
  patching: a future sprint reviewing hook dependencies should start
  from this list.

Fixing these was explicitly out of scope: this sprint's mandate was
formatting/lint **infrastructure**, not a general code-quality sweep,
and neither warning class blocks CI today.

## 8. Remaining recommendations (not executed this sprint)

1. **Finish the pre-commit hook** per the exact steps in §4, from any
   environment with access to the project's private package registry
   mirror.
2. **Triage the 5 `react-hooks/exhaustive-deps` warnings** (§5) as a
   small, dedicated follow-up — each requires reading the specific
   component to judge whether the missing/unnecessary dependency is a
   real bug or intentional.
3. **Consider whether `package-lock.json` should exist at all.** This
   repo carries both `bun.lock` (what CI actually installs from) and a
   committed `package-lock.json` that nothing in `package.json`'s
   scripts or `.github/workflows/ci.yml` ever reads. Keeping a second,
   unused lockfile in sync is itself a source of future drift (as this
   sprint's own investigation had to work around) — worth a deliberate
   decision (remove it, or document why it's intentionally kept) rather
   than leaving it as an accident of history.
